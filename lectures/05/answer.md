## 宿題

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  `app/config.py` の中にある `RAG_TOP_K` の数値を、初期設定の `5` から `1` に書き換えて動きを比べました。

- 比較した質問と、固定した条件（モデル・対象資料など）：
  - 使用モデル：`gemini-3.5-flash-lite`
  - 質問文：「第2回の説明では、LoRAは何を固定し何を学習しますか? QLoRAは何を加えますか?」

- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

| 比較項目 | 変更前（`RAG_TOP_K = 5`） | 変更後（`RAG_TOP_K = 1`） |
| :--- | :--- | :--- |
| ツールの呼ばれ方 | `search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})`（1回） | `search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})`（1回） |
| 引用根拠 | 第2回・PDF p.51, p.52 | 第2回・PDF p.52 のみ |
| 時間 | 2.56 秒 | 2.90 秒 |
| トークン数 | 入力 3,028 / 出力 159 tokens | 入力 1,191 / 出力 243 tokens |
| 推定コスト | $0.001306 USD | $0.000965 USD |

- 改善した例と、残る失敗・制約：
  - **変更前（5件取得）**：p.51とp.52の両方から情報を拾って、全体の要点がコンパクトにまとまっていました（出力 159 tokens）。
  - **変更後（1件取得）**：p.52の1ページだけしか渡していないのに、なぜか出力が243 tokensに増え、p.52に書いてある「NF4」や「二重量子化」といった細かい単語まで詳しく拾って答えてくれました。ただ、1ページしか見に行かない設定なので、答えが複数のページにまたがる質問だと情報が足りなくなりそうだと感じました。

- 気づき・疑問：
  - 検索件数を5件から1件に減らしただけで、入力トークン数が3,028から1,191へと半分以下になり、APIのコストも下がることを実感できました。
  - 最初は「検索するページを減らしたら回答も短く雑になるのでは？」と思っていましたが、今回は一番大事なp.52が1件目にヒットしたためか、かえってそのページの内容を詳しく説明してくれたのが意外でした。
  - 疑問として、今回はたまたま1ページに答えが収まっていたから良かったものの、実際のチャットボットでは `RAG_TOP_K` をいくつくらいに設定しておくのが一番バランスが良いのか気になりました。また、取得するページ数を減らしたのに回答までの時間（2.56秒→2.90秒）が少しだけ長くなったのは、その時々のAPIの混雑具合による誤差なのかどうかも気になりました。
